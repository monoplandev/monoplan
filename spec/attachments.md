# Attachments

Status: **decided 2026-11-24. Phases 1 (server), 2 (core) and 3 (web) built
the same day; the rest is plan.** What they do that this text did not first
say is under "As built". The web surface is covered by unit tests and has
not been run in a browser.

Files attached to items. The bytes are online-only: they live on the server as
encrypted blobs and are fetched on demand. The doc carries only the metadata
and the key, so an offline device still shows what is attached, by name.
Supersedes the image sketch in `notes-plan.md` §5, which becomes a consumer of
this surface.

## Shape

Two records, each the authority on one thing:

- **The doc says what is referenced.** A root `files` map holds one entry per
  attachment: its name, its size, its key, and the item that owns it.
- **The server says what bytes exist.** A `doc_files` row per stored blob,
  with its size and age. The server cannot read the doc, so it never knows
  whether a blob is still referenced.

An **orphan** is the difference between the two, and only a client can compute
it: list the server's rows for a doc, subtract the doc's `files` map.

## Doc layout

`doc.get_map("files")`: `LoroMap<FileId, entry>`. Additive within schema v4,
as the focus container was within v2: a client that does not know it never
projects it.

`FileId` is 32 lowercase hex characters (`[0-9a-f]{32}`, the item id grammar),
random, generated by the attaching client.

Each entry is one **atomic plain map** (a single LWW value, as `place`):

| Field | Type | |
|---|---|---|
| `item` | string | the id of the owning item |
| `name` | string | file name as attached, at most 255 bytes |
| `mime` | string | media type as the attaching client saw it; display and open-with only, never trusted |
| `size` | i64 | plaintext bytes |
| `key` | bytes (32) | the file key (below) |
| `created_at` | i64 | unix millis |
| `created_by` | string? | account id, on shared workspaces; self-asserted like the item register |
| `to_purge` | i64? | unix millis the attachment was removed; present ≡ **marked for purge** (below) |
| `destroy` | bool? | with `to_purge` only: the removal is permanent, the server destroys the bytes at once instead of tombstoning them (below) |

A file has **one owner item**, named by the entry. There is no per-item list
of file ids: an item's attachments are the entries whose `item` is its id, in
`created_at` order, read through a projection index. This keeps one container,
no mergeable child to create on first attach, and no item-side id that can
point at a missing entry. The cost is that a file cannot be attached to two
items; attach it twice.

Rename replaces the entry whole, and so does the purge mark. Nothing else
about an entry changes after it is written.

### Marked for purge

Removing an attachment does not delete its entry. It writes `to_purge` on it
(decided 2026-11-24, replacing delete-then-`DELETE`): the entry leaves every
view at once and stays in the doc as the durable instruction to remove its
blob. The instruction syncs like any other change, so a removal made offline
is acted on by whichever member's client is next online, the removing device
included, instead of waiting for the owner's sweep to notice a blob no entry
names.

A mark is one of two kinds (decided 2026-11-25). A **destroying** mark
(`destroy: true`) is a deliberate, permanent removal: `remove_file` and the
hard delete of an item. The client sends `DELETE` and the server removes the
row and the bytes on that request. Neither is an undo step, so
nothing can ask for the bytes back. A **plain** mark is the release half of a
cross-doc move or the sweep's ownerless entry: the client sends
`POST .../tombstone`, because an undo of the move or a late reference can
still want the file inside the grace period.

An entry therefore has three states: **live**, **marked** (`to_purge` set,
blob still stored), and **gone** (entry deleted, after the server destroyed or
tombstoned the blob). Only a live entry is in `ItemView.files`, has a key to read, or can
be renamed. A marked entry still holds its id: attaching under it is refused.

Later consumers reference a file by id and never hold bytes or keys
themselves: a notes image embed (`notes-plan.md`) carries `image: { id, w, h }`
and resolves the rest through the entry.

### Mutations

Each is one commit, and one undo step unless it says otherwise.

- `attach_file(item_id, file_id, name, mime, size, key)`: writes the entry.
  Called only **after** the upload has succeeded (below).
- `rename_file(file_id, name)`.
- `remove_file(file_id)`: marks the entry for purge, destroying. Permanent:
  origin `"file-remove"`, excluded from undo (undo steps over it to the edit
  before; undoing the attach of a removed file does not bring it back). The
  web asks for confirmation first.
- **Hard delete** of an item (`delete_binned`, `empty_bin`) marks its
  entries for purge, destroying, in the same commit (which already drops the
  undo history).
- `forget_files(file_ids)`: deletes the entries among them that are still
  marked, once the server has tombstoned their blobs. Origin `"sweep"`,
  excluded from undo, no event. `files_to_purge()` lists what is waiting,
  `files_to_destroy()` the destroying subset.
- **Bin keeps.** A binned item keeps its entries and its blobs, so restore
  never loses a file.
- **Duplicate** does not copy attachments (first pass).

`ItemView` gains `files` (the entries without their keys); rows show a count.
An `AppEvent::ItemFilesChanged` fires on local writes, imports and undo.

### Export / import

`export_json()` lists each item's attachments as `{id, name, mime, size}`,
without keys. `import_json()` ignores them: the bytes are not in the dump and
the ids mean nothing in another doc. An export archive that carries the files
is open.

## Encryption

Each file gets its own **random 32-byte file key**, stored in its entry. The
entry rides the doc, so it is sealed under the doc's DEK like every other op;
holding the doc is holding the keys to its files.

The blob is `nonce (24 bytes) || XChaCha20-Poly1305(file key, plaintext)`,
sealed in one shot (`crypto.md` §3; no streaming at this size cap). The server
stores it as one opaque body.

Why a key per file and not the DEK directly:

- **Cross-doc move without re-encryption.** The key travels with the entry, so
  the server copies ciphertext between docs and no client downloads anything.
- **No substitution.** A blob served under the wrong id fails to open, with no
  associated data needed.

The server learns, per doc: how many files, their sizes, when each was stored
and by which device. It does not learn names, types, or which item owns what.

## Server

Bytes never go in sqlite: a 25 MiB row would bloat the WAL and every database
backup. They go behind a small **blob store** interface keyed by
`<doc_id>/<file_id>`: `put`, `get`, `copy`, `delete`, `delete_doc`. The
`doc_files` row is the record; a stored object with no row is garbage. Two
backends, chosen in `server.toml`:

- **Directory** (default, built first): `<attachments_dir>/<doc_id>/<file_id>`.
  What self-hosters run, and what the tests and local dev run, so the server
  stays one binary and one data directory with no object store beside it.
- **S3-compatible** (the hosted deployment; built when it needs it): the same
  keys in one bucket. `copy` is a server-side `CopyObject`.

The routes are the same over both, and the server proxies the bytes in the
first pass, which is fine at this cap. On S3, `GET` may later answer with a
redirect to a short-lived presigned URL, and `PUT` may become presign plus a
completion call; both are optimisations that leave the records and the
garbage rules alone. Bucket lifecycle rules are not used: purge is driven by
the rows.

```sql
CREATE TABLE doc_files (
  doc_id        BLOB NOT NULL REFERENCES docs(id),
  id            BLOB NOT NULL,              -- 16 bytes, client-chosen
  bytes         INTEGER NOT NULL,           -- stored (ciphertext) size
  device_id     BLOB,                       -- uploader; not surfaced to clients
  created_at    INTEGER NOT NULL,
  deleted_at    INTEGER,                    -- tombstone; purged after the grace period
  PRIMARY KEY (doc_id, id)
);
```

In `001_init.sql`, edited in place; `storage.md` holds the authoritative copy.

### Routes

All authed by the device token; every one requires an active membership of
the doc and answers 404 to anyone else.

```
PUT    /api/docs/:doc_id/files/:file_id           -- raw body; store a blob
GET    /api/docs/:doc_id/files/:file_id           -- the blob; 410 if tombstoned
DELETE /api/docs/:doc_id/files/:file_id           -- delete for good, row and bytes (any member)
POST   /api/docs/:doc_id/files/:file_id/tombstone -- tombstone (any member)
POST   /api/docs/:doc_id/files/:file_id/restore   -- clear a tombstone (any member)
POST   /api/docs/:doc_id/files/:file_id/copy      -- { to_doc_id }; member of both
GET    /api/docs/:doc_id/files                    -- { doc_bytes, used_bytes?, limit_bytes?, files: [{ id, bytes, created_at, deleted_at? }] }
```

- **PUT** is a single request, no chunking or resume. `Content-Length` is
  required and capped at 25 MiB plus the 40 bytes of nonce and tag: 413 over
  the cap, 507 `quota` if it would take the doc's owner over their allowance. The body is
  stored, then the row is inserted (the directory backend writes a temp file
  and renames it into place, and removes stray temp files at startup). An id that already exists is 409, which a
  retrying client treats as success (the id is random and its own).
- **Quota** belongs to the **doc owner's account**, pooled over every doc
  that account owns (decided 2026-11-24, replacing a per-doc limit: with a
  per-doc limit each new workspace was more space). It is the sum of `bytes`
  over the rows that are not tombstoned in those docs, against one
  server-wide `max_account_file_bytes` (default 1 GiB). A member's upload to
  a shared workspace counts against its owner, not the member. The list
  route gives `doc_bytes` (this doc alone) to every member, and the pooled
  `used_bytes` / `limit_bytes` to the owner only: to a member they would
  say something about workspaces the member is not in. No per-account
  override and no plan logic yet.
- **`DELETE` deletes** (any member, 2026-11-25): the bytes and then the row,
  at once, tombstoned or not; 404 when there is no row. It is what a
  destroying purge mark sends. Bytes first, so a request that fails between
  the two can be repeated.
- **Tombstone otherwise.** `POST .../tombstone` stamps `deleted_at`. A purge task
  removes the row and the bytes **30 days** later. `restore` clears the stamp
  inside that window, and is 507 `quota` if the bytes no longer fit: a
  tombstoned row does not count towards the quota, so an unchecked restore
  would let delete / upload / restore store without bound.
- **Copy** duplicates the row and the bytes into the target doc under the same
  id, counted against the target owner's quota. 409 if the id exists there.
  A copy between two docs of one owner needs room for both, because the
  source is only tombstoned afterwards; a nearly full account cannot move a
  large file between its own workspaces.
- **Cascade.** Deleting a doc (`DELETE /api/docs/:id`, account deletion)
  removes its rows and its stored objects outright, no grace period. A removed
  member loses every route from the commit, as with the doc itself, and keeps
  whatever they already downloaded.

No WS frames. Other devices learn of an attachment from the entry arriving in
the doc.

## Client flows

**Attach** (online only; refused offline in the first pass, since a queue of
pending uploads is the one place local bytes would leak in):

1. Generate the id and the file key, seal, `PUT`.
2. On 2xx or 409, `attach_file`.

Upload first, reference second. A crash between the two leaves a blob no doc
names, which the sweep collects; the reverse order would publish an entry
other devices cannot open.

**Open.** `GET`, open with the entry's key, hand the bytes to the platform
(blob URL on the web, a temp file on native). Nothing is fetched until the
user opens the file. Decrypted bytes are held for the session at most and
never written to the local store.

**Purge.** Any member's client, when online: read `files_to_purge()`,
`DELETE` the blobs of the ids in `files_to_destroy()` and tombstone the rest,
and pass the ids the server answered (2xx, or 404 / 410:
already gone) to `forget_files`. Run after a local removal or hard delete, and
on connect once the replica is caught up, which is what picks up a removal
made offline or on another device. Two devices doing it at once is harmless:
a repeated tombstone keeps the first stamp, a repeated `DELETE` is a 404, and
`forget_files` skips an entry that is already gone. An entry that is live
again by then (an undone release) is skipped too, and its blob comes back
through the 410 path below.

**Missing bytes.** A 404 or 410 on an entry the doc still holds renders the
row as unavailable. On 410 the client calls `restore` and retries: a reference
that outlived its tombstone (a stale device, a concurrent edit) wins inside
the grace period.

**Cross-doc move** (`sharing-plan.md` "Cross-doc move") extends the existing
order: `copy` each file to the target doc, adopt (the export form carries the
entries, keys included), release. The release marks the source entries for
purge, so the source blobs go by the ordinary purge. A failed copy aborts the
move before anything is written. Adopt replaces a marked entry of the same id
(the item moving back to a doc it left); the host then finds the id already on
the server (409 on `copy`) and restores it instead.

## Garbage

Two ways a blob stops being wanted:

1. **Deliberate.** `remove_file`, a hard delete, or the release half of a
   cross-doc move. The entry is marked for purge and any member's client
   finishes it ("Purge" above): the first two destroy the bytes, the release
   tombstones them. Nothing here depends on the sweep.
2. **Orphans.** A blob no entry names (an upload whose commit never landed;
   an attach or an adopt that was undone, which deletes the entry outright),
   or a live entry whose owner item is gone (one device attached while
   another hard-deleted the item).

Orphans are collected by a **sweep**, run only by the **doc owner's** clients,
only when the replica is caught up with nothing pending, at most once a day
per doc:

- Mark for purge the live entries whose `item` is not in `items` and whose
  `created_at` is over 24 hours old. Commit with origin `"sweep"`, excluded
  from undo. The ordinary purge then takes their blobs.
- `GET` the file list. Tombstone every row that is not tombstoned, is over
  24 hours old, and has no entry, live or marked.

The 24 hours covers an upload still on its way to its commit. The 30 days
covers everything else a sweeping client cannot see: a device that has been
offline, a reference revived by a merge. The sweep never causes bytes to be
destroyed directly: only a destroying mark does that, and for the rest the
server's purge does, after the window.

## Not in the first pass

- Offline attach (an upload queue) and any offline copy of the bytes.
- Thumbnails and inline previews in rows.
- Files shared between items; attachments on a duplicate.
- Chunked or resumable upload; a cap above 25 MiB.
- A per-account override of the allowance, and plans.
- An export archive that includes the files.

## As built

Phase 1, the server (`server/src/files/`, `server/src/http/file_routes.rs`,
tests in `server/tests/files.rs`).

- **Blob store** is an enum, `BlobStore::{Dir, Mem}`, not a trait object; S3
  is a third variant. `Mem` exists so the other test suites need no directory.
- **Config.** `attachments_dir` (`MONOPLAN_ATTACHMENTS_DIR`; unset means an
  `attachments` directory beside the database file, which is already inside
  the writable path of the systemd unit and the Docker volume) and
  `max_account_file_bytes` (`MONOPLAN_MAX_ACCOUNT_FILE_BYTES`).
- **PUT refusals come from the headers**, before the body is read: 411
  `length_required` with no `Content-Length`, 413 `too_large` over the cap,
  400 under 40 bytes (not a sealed file), 400 for an id that is not 32
  lowercase hex characters, 409 for an id already there (tombstoned
  included), 507 `quota`. The quota is checked again in the transaction that
  inserts the row; bytes stored for a row that then fails that check are
  removed.
- **Restore checks the quota** (above). Restoring a live file is a no-op 200.
- **Repeating a tombstone keeps the first stamp**, so it cannot extend the grace
  period.
- **Copy** of a tombstoned source is 410.
- **Purge** runs at startup and hourly. It deletes the row first (re-checking
  the tombstone, so a restore that lands mid-pass keeps the file) and the
  bytes second. With PUT's bytes-then-row order this means a crash can leave
  a stored object with no row, never a live row with no bytes. Nothing
  collects such objects yet.
- **Bodies are buffered whole** in memory on the way in and out, which the
  25 MiB cap allows.

Phase 2, the core (`core/src/doc.rs`, tests `files_*` beside it).

- **Types.** `ItemFile` is the entry as an item shows it (`id`, `name`,
  `mime`, `size`, `created_at`, `created_by`; no key, no owner).
  `ExportFile` is the export form. `size` is `u64` in Rust and an i64 in the
  doc.
- **Reads.** `ItemView.files` in `(created_at, id)` order, from a disposable
  index of the container that is rebuilt whole whenever it changes.
  `Doc::file_key(file_id)` gives the key, `Doc::file_owner(file_id)` the
  owner item id. An entry that is malformed, or sits under an id that is not
  32 lowercase hex characters, reads as absent.
- **`attach_file`** refuses an id the doc already holds, a key that is not
  32 bytes, and a name that is empty after trimming, over 255 bytes or
  holding a control character. `mime` may be empty (unknown) and is at most
  255 bytes. It stamps `created_at` and, when the doc has an author,
  `created_by`. The item may be binned.
- **`rename_file`** to the name it already has is a no-op with no commit.
- **Removal with the item.** Hard delete and `release_items` (the giving
  half of a cross-doc move) both mark the items' entries for purge in the
  same commit. Undoing a release puts the item back and clears the marks.
- **Undo after the purge finished** (`release_items`, then `forget_files`,
  then undo) brings the entry back live. Its blob is tombstoned by then, so
  the host restores it on the 410.
- **`file_key` / `file_owner`** answer for live entries only.
- **Events.** `ItemAdded` carries `files`; `ItemFilesChanged { id, files }`
  carries the whole list after a change. Remote frames and undo are
  translated to that one event, not a resync. An entry whose item is not in
  the doc emits nothing and waits in the index, so it shows if the item
  arrives later.
- **Export.** `export_json()` lists `{id, name, mime, size}` per item;
  `import_json()` ignores it. `export_items()` adds `key` (64 hex
  characters), `createdAt` and `createdBy`, and `adopt_items()` writes the
  entries from them, dropping one with no key, malformed fields or an id the
  doc already holds. `move_items_across_docs` moves entries only: the blob
  copy before and the tombstone after are the host's.
- **Fingerprint** covers every well-formed entry, marked ones too: owner,
  key and purge mark included.
- **Wasm** (`core/web`): the `itemFilesChanged` event, and `files` on
  `itemAdded` and on the item JSON. No mutation is bound yet; the web store
  ignores the event until phase 3.

Phase 3, the web (`js/web/src/sync/files.ts` the host half,
`FilesField.tsx` the surface, tests in `js/web/test/files.test.ts`), with
the core and wasm additions it needed.

- **Core.** `seal_file` / `open_file` in `core/src/crypto/aead.rs`
  (`crypto.md` §3). `Doc::mark_ownerless_files(created_before)` is the
  sweep's doc half: it marks, origin `"sweep"`, no event, and the ordinary
  purge finishes the job. `Doc::stored_file_ids()` is every key of the
  container, including entries this build cannot read, so a sweeping
  client never tombstones the blob of an entry in a newer shape.
- **Wasm.** `sealFile` / `openFile`, and on `Replica`: `attachFile`,
  `renameFile`, `removeFile`, `fileKey`, `filesToPurge`, `forgetFiles`,
  `markOwnerlessFiles`, `storedFileIds`. Not on the bare `Doc` class.
- **Ids and keys** are generated in the browser (`crypto.getRandomValues`):
  16 random bytes as hex for the id, 32 for the key.
- **Attach** refuses over 25 MiB before reading the file, cleans the name
  to what the core accepts (control characters out, cut to 255 bytes with
  the extension kept), and writes the entry only if the doc is still open
  when the upload returns. A row for the upload shows under the list until
  the entry lands, and stays with the reason if it fails (over the cap,
  storage full, offline, other).
- **Open always saves to disk.** The bytes go to the browser as a download
  typed `application/octet-stream`, never rendered in the app's origin: the
  media type is whatever a member of a shared workspace wrote, and an HTML
  or SVG blob opened in a tab would run with access to the local keys.
  Nothing is cached; every open fetches.
- **Housekeeping is pulsed.** The runtime pulses a doc after each server
  frame for it and every doc when the socket comes up. A pulse that finds
  entries marked for purge and no changes the server has not acknowledged
  settles at once (2026-11-25), so a removal is sent as soon as its mark
  has synced: the push's ack is itself a frame, and that is the pulse that
  acts. Any other pulse settles 3 seconds after the last one, and a settle
  does nothing while the doc has unacknowledged changes. After a purge that
  stopped on a failed request the doc's pulses wait the 3 seconds again
  until one completes. A settle is the purge, then the sweep if one is due.
  Nothing runs for a signed-out session.
- **Purge** stops at the first request that fails for a reason other than
  404 / 410 and forgets what was answered up to there. A file's own removal
  cannot be undone. An undo of a move that lands before the release's mark
  is acknowledged clears it with nothing sent; a later one brings the entry
  back live over a tombstoned blob, which the read path restores.
- **The sweep learns ownership from the list route**: the pooled quota
  figures come to the owner only, so their presence is the test. Every
  member's client therefore asks for the list once a day per doc and a
  non-owner stops there. The day is kept per doc in `localStorage`
  (`monoplan.files.sweep.<doc_id>`), stamped only once the list has been
  fetched and, for the owner, the doc has nothing unsent.
- **Cross-doc move** (`Workspace.tsx` `withFilesCopied`, around the three
  gestures that cross docs): `copy` for every live file of the crossing
  items, then the move exactly as before. 409 on a copy restores the id in
  the target; 410 restores the source and copies again; 404 at the source
  (the file was already unavailable) is passed over. Any other failure, or
  being offline, moves nothing and says so in an alert. Blobs copied
  before a later copy failed are orphans for the target owner's sweep.
- **Rows** show a file glyph and the count on Open items, beside the
  subtask count. The task surface shows the section only once the item
  exists, and not at all to a signed-out session with no files.
- **No rename on the web** (cut 2026-11-24): a file keeps the name it was
  attached under. `Doc::rename_file` and the wasm `renameFile` stay; the
  store and the surface do not call them.
- **Storage row** (2026-11-25, not browser-checked): Settings → Account
  shows the pooled `used_bytes` of `limit_bytes` ("12.3 MB of 1 GB used"),
  read from the list route of the Home doc (which the account always
  owns) each time the section is entered. A dash until the first read
  lands, and while offline.
- **Not built:** drop or paste to attach, upload progress, a retry on a
  failed upload row (dismiss and pick again), image previews.
